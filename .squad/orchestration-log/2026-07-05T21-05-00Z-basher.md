## Incident summary

Production meal-image uploads at meals.themartinez.cloud returned HTTP 500. Root cause:
- No `IMAGE_STORAGE_ROOT` env var set in the prod Deployment.
- No durable volume mounted; the app tried to write to `/app/.data/images/` which is
  root-owned; the `node` user (uid/gid 1000) had no write permission → `EACCES`.
- `replicas: 2` (HPA 2–3) meant any pod-local path would be non-shared anyway.
- Three catch blocks in `routes/images.ts` swallowed errors silently → generic 500 with
  no server-side trace.

## Basher's attempt

Basher authored a fix in this repo's `k8s/` folder:
- New `k8s/image-pvc.yaml` (ReadWriteOnce, 5Gi, `local-path` storageClass).
- `deployment.yaml`: added PVC volumeMount + `IMAGE_STORAGE_ROOT=/data/images` env +
  `fsGroup:1000` securityContext.
- Reduced `replicas: 2 → 1` (required by RWO — only one pod can bind the volume).
- `kustomization.yaml`: added `image-pvc.yaml` to resources.
- `k8s/README.md`: updated backup docs to reflect the wired PVC.

`kustomize build k8s/` and `kubectl apply --dry-run=client -k k8s/` rendered clean.

## Wrong-repo pivot — PR #182 CLOSED

**The meal-planner `k8s/` folder NEVER reaches production.**

Production is managed by the **`raspberry-pi-kubernetes-cluster`** GitOps repo (ArgoCD).
When this was discovered, PR #182 was CLOSED and the branch deleted.

The correct fix — a **Longhorn ReadWriteMany PVC** (preserving the HPA at 2–3 replicas) +
`IMAGE_STORAGE_ROOT=/data/images` + `fsGroup:1000` — was filed as **issue #104** in
`raspberry-pi-kubernetes-cluster` and is in-flight there, owned by Dallas (GitOps engineer).

## Key lesson recorded

> Production infra fixes for meal-planner belong in `raspberry-pi-kubernetes-cluster`,
> not in this repo's `k8s/` folder. Single-replica RWO would break the HPA — always
> prefer Longhorn RWX for multi-replica deployments.

Both lessons are now recorded in `.squad/decisions.md`.
