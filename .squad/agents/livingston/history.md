## 2026-08-03T11:00:32-0400 — Grid matcher hardening: phrase-specificity (token collisions)

- PROBLEM (found sideways by Saul while authoring the seed): multi-word ingredients sharing a token collided. "Ground beef" + "Beef broth" both reduced to `{beef}` (because `ground` was a stop word), so a step mentioning "beef" matched BOTH — corrupting the first-use permutation and spans. Saul worked around it by renaming his ingredient "Beef broth" → "Broth".
- TWO coupled causes: (1) descriptor words (`ground|diced|fresh|…`) were in the stop list and DISCARDED, erasing the very signal that disambiguates "Ground beef" from "Beef broth"; (2) `mentionedRows` matched on ANY shared token, so a lone "beef" claimed both rows.
- FIX in `packages/shared/deriveRecipeMatrix.ts` (DERIVED branch only — authored still passes through untouched):
  - Split the old `STOP_WORDS` into `QUANTITY_STOP` (removed entirely) and `MODIFIER_WORDS` (kept but tagged `mod`). A modifier adds phrase specificity but can NEVER anchor a match — an ingredient matches only via a **core** (non-modifier) token. This stops a bare "fresh"/"diced" in a step from dragging in every fresh/diced ingredient.
  - Replaced any-token matching with **phrase-specificity claiming**: tokenize the step into ordered tokens; for each ingredient find maximal runs of step tokens that all belong to it AND are truly adjacent; occurrence specificity = # distinct ingredient tokens; each step position is won by the max-specificity occurrence; an ingredient matches iff it ties the winning specificity at ≥1 of its positions. Ties → BOTH match.
  - **True adjacency**: `tokenize` now flags `gapBefore` — only whitespace counts as adjacency, so a dropped stop word or punctuation between two words marks a gap. Critical: "chicken **in** broth" must NOT collapse into the compound "chicken broth" (both the protein and the broth are genuinely used); "ground beef" (whitespace-adjacent) DOES form a phrase.
- RULING on genuine ambiguity (mine, deliberate): a lone shared token with no distinguishing adjacency → MATCH BOTH (status quo). We only ever DROP a match when a strictly more specific adjacent phrase explains the exact region — never on a guess. Follows the label-work principle: prefer the error that doesn't state something false. A wrongly-suppressed match under-brackets (mild); a wrongly-added one corrupts ordering AND over-brackets (worse).
- MEASURED on Brandon's real 74-meal library (read-only container `saul-mealdb`, 61 PROCESS steps): old-vs-new matcher changes exactly **1 step** — "Weeknight Thai Green Curry" step 4 "Finish with Thai basil…" no longer false-matches "Thai eggplant" (shared "thai" token). **1 false match removed, 0 added.** Honest finding: on the current library the collision class was RARE — matching was a MINOR contributor to the 43% over-bracket rate; shopping-vs-use ORDERING (P1-10) is the dominant cause. First adjacency-naive draft dropped a 2nd step ("Poach chicken in broth") wrongly; the `gapBefore` refinement fixed that (chicken thighs preserved).
- SEED RENAME CAN BE REVERTED: reconstructed Saul's Beef Chili with the natural "Beef broth" name → derives PERFECTLY. "Add the ground beef and brown it" spans Ground beef ONLY (Beef broth suppressed despite sharing "beef"); "…and broth…" matches Beef broth via the distinct "broth" token. Zero over-bracket. Told the coordinator Saul can restore the natural name.

REST + MCP inherit automatically. api/src needed NO change — the matcher lives entirely in shared; the api just calls `deriveRecipeMatrix`. Confirmed in code.

## 2026-08-03T11:00:32-0400 — Grid matcher hardening: ingredient-side full-consumption (mirror of a008feb)

- PROBLEM (found by Saul in Greek Salad): the mirror image of the phrase-specificity fix. There, a longer STEP phrase disambiguated a shared token. Here the disambiguation lives on the INGREDIENT side: ingredients `Olives` + `Olive oil`, step says bare "olives" → my equal-specificity tie rule matched BOTH, sweeping Olive oil into the feta+olives step (span 3..5 instead of 3..4). - FIX in `packages/shared/deriveRecipeMatrix.ts` (DERIVED branch only; authored still passes through untouched): added a SECOND tiebreak after step-side `spec`. Each occurrence now records `fullyConsumed` (= the run matches ALL of the ingredient's CORE tokens). Per position, `hasFull[p]` = any spec-winner there is fully consumed; a candidate claims p iff `o.spec === bestSpec[p] && (!hasFull[p] || o.fullyConsumed)`. So "olives" (fully consumes `Olives`, leaves `oil` in `Olive oil`) picks `Olives` and suppresses `Olive oil`.
- CRITICAL DESIGN: full-consumption is BINARY (leftover core vs none), NOT a count. First tried a count (min unmatched-core) — it FAILED 2 tests by wrongly evicting Birria's correct-but-longer `beef chuck roast` (2 leftover core) in favour of `beef broth` (1 leftover) on "braise the beef …". Neither is fully consumed there, so both must stay. Only a candidate that leaves NOTHING unaccounted-for may evict others. Binary passes all tests.
- NO under-matching regression: full-consumption only evicts when a CO-COVERING occurrence at the SAME position is fully consumed. A lone candidate always matches regardless of leftover core → a recipe with only "Onion powder" (no plain onion) still matches a step saying "onion". Verified by targeted test + reasoning. Leftover MODIFIER tokens never penalise (only `core` checked), so "Fresh basil" vs "Basil" on "basil" → both match.
- RULING on genuine ambiguity (mine, held the line): when NEITHER co-covering name is fully consumed (e.g. `Tomato paste` + `Tomato sauce`, step "tomato"), keep BOTH — full-consumption vs leftover-core is an objective distinction, not a guess, and where it IS a guess we keep both. Same label-work principle: prefer the error that doesn't state something false.
